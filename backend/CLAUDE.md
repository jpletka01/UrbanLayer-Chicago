### WS2 upcoming-zoning snapshot and Profile signal (PRs 1–3)

`legislation/pending.py` is the pending half of the existing daily `legislation.sync` oneshot; there is still only one Clerk caller in the serving stack. It asks for every non-final zoning/code matter, validates explicit Clerk states 2–5, retains zoning reclassifications plus Title-17-looking text matters, fetches full detail serially, follows original/substitute/supersession links, and refuses to choose between two current matters in one lifecycle. It never downloads a PDF or calls a model. Attachment metadata is allowlisted and EDS is rejected by type and filename before persistence.

`legislation/pending_store.py` owns `backend/data/pending_legislation.db` (schema v2; v1 migrates in place): `sync_runs`, current `matters`, `actions`, permitted `attachments`, `relations`, parsed `segments`, and Address-Points `locations`. The daily sync resolves every clean title range before the one-transaction replacement; a source failure appends the attempt and preserves the last-good rows. `internal.pending_legislation` exposes actual placed/unplaced matter and location counts as well as parse coverage, lifecycle collapses, exclusions, and the latest failure in Data Health.

`legislation/upcoming.py` is the **request-path read-only reader** used only by `/api/scorecard` after parcel identity is reconciled. It opens SQLite `mode=ro`, never calls Clerk or Address Points, pins exact PIN/range matches first, then uses a SQLite 0.5-mile bounding box plus haversine filtering for nearby matters. `UpcomingZoningSummary` separates `ready | stale | unavailable` freshness from `complete | partial` placement; a ready/complete empty list is the only healthy zero. After 14 days it returns unavailable and no filings. The Profile shows current map filings as applicant proposals (never approvals); chat/report/maps stay out of scope. Provenance facts split the Clerk record from UrbanLayer's Address Points placement. Tests: `test_pending_legislation.py`; the 21-title hand-labeled panel records 76.19% conservative coverage, 100% precision, zero wrong-street matches at `tests/fixtures/clerk/pending_title_panel.json`.

**PR3 — pending Title 17 text impacts (`legislation/impacts.py` + `pending_impacts.json`).** The Profile names a pending Title 17 amendment only when a committed, human-read review of its **current** record maps it to a rule or fact the Profile shows AND the parcel deterministically satisfies the mapping. `backend/pending_impacts.json` is keyed by lifecycle id (the original O-number); `reviewed_record` is the exact record whose text was read, so a newer substitute makes the review `outdated` (unreviewed) until re-read. `basis: ordinance` (the Legislation PDF was read, never an EDS) is the only basis that may carry `impacts`; `basis: title` can only say "no Profile fact". An impact has `sections` (Title 17), `fact_ids` (validated against `provenance.FACTS`, plus `note.*` for coverage notes), `applies_when` (`zone_patterns` regexes on the upper-case zone class, `overlays_any`/`overlays_none`, `facts_all`, `address_ranges` for street designations), `reach` (`parcel`, or `untested` when a boundary/lot-width condition can't be tested, which is said, never claimed) and the "could change" wording. `main.scorecard()` runs `impacts.for_parcel` **after** `build_provenance` because the facts the Profile actually shows decide relevance, then merges `provenance.text_impact_entries` (Clerk record = tier B/official record; relevance = our calculation, source `internal.pending_impact_review`). `UpcomingZoningSummary` gains `text_impacts[]` and `text_review` (`complete | incomplete | unavailable`, counts, the unreviewed/outdated list): only `complete` may say none map; a missing review, an outdated one or an unavailable snapshot never reads as "none". A title keyword never relevance-matches; nothing here touches a current-law number. Data Health `internal.pending_impact_review` (`probes.probe_pending_impact_review`): warn at 14 days since introduction, alarm at 45, any invalid review entry alarms, no judgement without a fresh pending snapshot. The 2026-10-28 population is 48 pending Title 17 text matters (recorded at `tests/fixtures/clerk/pending_title17_text_2026-10-28.json`): 13 carry impacts, 35 are reviewed as no-Profile-fact (6 from the ordinance text, 29 from the title, flagged in the PR). Monthly routine: `claude-context/guides/code-refresh.md`. Tests: `test_pending_impacts.py`.

## Patterns

- **New Socrata module**: copy `business.py` — same `socrata_get()` pattern with `community_area` filter.
- **New ArcGIS module**: copy `zoning.py` — same spatial query pattern, change endpoint + layer ID.
- **Domain orchestrator**: `asyncio.gather(return_exceptions=True)` → build summary → graceful degradation on failures.
- **External queries**: always use TTLCache, `httpx.AsyncClient`, return `None` on failure. All modules use shared HTTP clients (module-level `_get_X_client()` pattern, same as `socrata.py:get_shared_client()`). Functions accept optional `client` parameter for testing.
- **Tests**: mock external APIs in unit tests, `@pytest.mark.integration` for real-API tests. Cache-clearing autouse fixture in `conftest.py`.

## Production Configuration

- **Retrieval concurrency**: `_RETRIEVAL_SEM = asyncio.Semaphore(8)` in `main.py` limits concurrent retrieval tasks in `_retrieve()` and `_fetch_map_rows()`. Increased from 4→8 after server upgrade to 8GB RAM (2026-06-06).
- **ML model preloading**: Embedding model (`bge-base-en-v1.5`, ~500MB) is preloaded at startup via `run_in_executor` in the `lifespan` handler. Startup is **blocking** (not `create_task`) so health checks don't pass before models are loaded.
- **Reranker**: **DISABLED — and OFF BY DEFAULT since 2026-07-09** (`reranker_enabled=False` in `config.py`; the `RERANKER_ENABLED=false` in `docker-compose.prod.yml` is now belt-and-suspenders, and the Dockerfile no longer bakes the ~1GB cross-encoder into the image — it downloads lazily if ever re-enabled). Originally disabled in prod 2026-06-16 — it hung `/api/report` → 504. Root cause (profiled 2026-06-18): unbounded rerank concurrency (the report fires 5 parallel `semantic_search` → 5 torch `predict()` thrashing the 4-vCPU box) compounded by a 3× oversized batch (60 pairs reranked to return 3). The concurrency/batch fix (top-20 batch, single-worker `_get_rerank_executor()` in `vector_search.py`, configurable `reranker_torch_threads`; commit `e59990b`) landed and is core-independent (native 5-way 35.7s→12.4s) **but was VERIFIED-TOO-SLOW on the real prod box 2026-06-18** — a single 20-pair `predict()` is still ~40s on these vCPUs, so the report path stayed ≫180s. **Resolved instead by removing the reranker from the report path entirely** via the precomputed zoning cache (`zoning_cache.py`, deployed & verified live 2026-06-18, `main` @ `69d8481`). The flag stays `false`; re-enabling for chat would need a faster/ONNX-quantized cross-encoder. Full record: `claude-context/archive/2026-06-16_report-oom-reranker.md`.
- **SSE error handling**: `_event_stream()` wraps fatal calls (`db.count_user_messages()`, `synthesize_query()`) and non-fatal calls (`compute_analytics()`, `_build_map_response()`) in separate try-except blocks to prevent generator crashes before any SSE chunk is yielded.
