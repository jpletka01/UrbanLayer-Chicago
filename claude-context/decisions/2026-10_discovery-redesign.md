# Property Discovery redesign: engineering decisions

The redesign of the Property Discovery page (`/discovery`), phase by phase. Format: see `README.md` in this folder. The plan lives outside the repo (local-only); the decisions below restate what a reader needs.

---

## Item 1: Phase 0, edits are drafts and a search runs only on "Update results" (2026-10-28)

**Decision: the page holds a draft and an applied query, and nothing is requested until the user presses Search, Enter or "Update results".** `useDiscoverySearch` (new) owns both. The draft is the panel controls, the text and the sort. The applied query is the last `response.cqs` the server evaluated. Removing a chip, editing a control, "Clear all" and the zero-state "remove" buttons only change the draft. One press sends one search/pins pair, however many edits came before it. *Why explicit apply and no debounce:* it was the owner's call (2026-10-29), the way a listings site waits for its search button. It also protects the server: a client abort does not stop the Python thread already scanning the index (plan section 3.3), so one request per press, not per edit, is what keeps the box from queueing scans. *Alternatives rejected:*
- **Auto-apply about 0.7 s after the last edit.** Rejected by the owner for now. It would still fire a full scan whenever a user pauses mid-thought, and a pause is not a decision. Revisit with a longer idle delay only after Phase 1 makes a search about a second or instant for repeats and undo.
- **A live search per edit (the old chip behaviour, made non-blocking).** Rejected: removing four chips would queue four 2 to 9 s scans, and only the last one matters.

**Decision: the previous evaluated results stay on screen while a refresh runs, dimmed and inert.** The rows, count, summary sentence, map dots and counted key are kept (about 55% opacity, `aria-busy`, `inert`, "Updating…" beside the count). Only the very first search, which has nothing to keep, shows "Searching…". A failed refresh keeps the previous results and shows an inline "Couldn't update. Retry" bar; a failed first search keeps the old "Search unavailable" message. *Alternative rejected:* skeleton rows or a spinner over the old list (still hides what the user was reading). *Inert, not just dimmed:* the stale rows must not be clickable or focusable, and Export, "Ask the analyst" and load-more must not act on a query that is being replaced. The cost is that the stale list cannot be scrolled while it loads.

**Decision: the chips strip renders from the draft; the summary, count and rows render only from `response.cqs` (INV-4 is narrowed, not broken).** The strip is the control surface, so it has to stay clickable mid-refresh and show what the user is asking for. A chip the server has not evaluated gets a dashed outline plus a screen-reader note; a removed chip stays, struck through, until applied, and one click restores it. The orange "Update results (n)" button counts filter changes (added, changed, removed) plus a changed sort and non-empty changed text. No sentence or number about results is ever derived from the draft. `01-invariants.md`'s PR-gate line "Frontend renders chips/summary from `response.cqs`, never from local pre-send state" is now true of the summary only: **the invariants file is not edited here and the owner should decide whether to amend its wording.** *Alternative rejected:* keep chips on `response.cqs` and block them during a refresh (the bug being fixed).

**Decision: text-derived filters are "carried", not copied into the panel.** A filter the server derived from free text is not in the panel, so the draft shows it from the applied cqs while the draft still has text. Removing one folds every carried filter into the panel as plain user filters and drops the text they came from (unless the user has already typed new text), the same fold the old one-tap relax did, so the removed chip cannot be re-added by the text. After a response lands with no edits made in flight, the panel is reconciled to the user-sourced filters the server evaluated, so a filter the server dropped does not leave a permanent pending change. *Alternative rejected:* copy text-derived filters into the panel on arrival. Editing the text would then accumulate the old text's filters instead of replacing them.

**Decision: abort the superseded fetch and keep the latest-issued-wins id guard.** `AbortSignal` is threaded through `lib/api.ts` and `searchClient.ts` (`runSearch`, `runPins`). An aborted request resolves to `null` like any failure, so the id check (not the signal) is what tells "superseded" from "failed". An apply that matches the search already in flight (same panel, text and sort) does nothing, so a double click cannot cancel and re-issue the same scan. Load-more and export re-issue the **committed** search, not one in flight and not the draft.

**Decision: the map keeps the previous dots, dimmed and not pickable, and the Item 30 checks still decide what replaces them.** While refreshing the points layer is at 35% opacity with no pick, hover or click handlers, no tooltip and no hover ring; the key keeps counting the previous model; a "Previous results, updating" chip says so. New dots replace the old only when data version, total and cardinality agree with the new list; otherwise the map is unavailable and the list stays (Item 30, unchanged). *Camera:* `fitBounds` runs for the first result and for later results while the user has not moved the camera since the last fit; once they have (Mapbox tags drag, wheel and the +/- buttons with an `originalEvent`; our own fit and the theme-swap `jumpTo` carry none), new results leave the camera alone and a "Zoom to results" button offers the fit. Theme swaps keep the camera (Item 31, unchanged). *Alternative rejected:* always refit (jerks the view the user chose) or never refit (the first search would land on a default view).

**Decisions about what stayed immediate.** A **recipe click** still replaces the draft and searches at once (it is itself the explicit "run this", and the auto-run of the first live recipe on load is untouched, Phase 2 owns removing it). Spanish is deferred by the owner: the new strings are in English first in `pages.json`; the `es` values added alongside are a first draft for the pre-merge Spanish pass, not reviewed copy.

**Why (evidence).** Plan section 3 (live audit of the production page on 2026-10-28, **taken on a busy box during an index rebuild, so absolute times are inflated**; the shape is what is solid): a chip removal blanked the whole results area (chips gone 33 ms after the click); removals took 2.3 to 2.6 s each for the recipe's own filters and did not return within 9 s once the query was broad; four removals were about 25 s of "Searching…"; each edit issued its own list and pins request pair. Probe ladder, one request at a time: 5,005 matches 2.05 s list / 1.22 s pins; 599,804 matches 4.0 s / 5.1 s; 949,014 matches 6.4 s / 6.7 s. The wait is server compute, so Phase 0 cannot make a search faster; it makes the user pay for one search per burst of edits and never see an empty page.

**Revisit if:**
- Phase 1 makes a search about a second (or instant for repeats): then auto-apply with a longer idle delay is worth re-testing against "Update results".
- Users forget to press Update results. There is no analytics for that today (Phase 0 adds only `ms` to `discovery_search`); the plan's Phase 2 events are what could show it.
- Stale results get mistaken for current ones despite the dimming and label.
- The owner decides the PR-gate wording in `01-invariants.md` should say chips are draft-driven.

**Numbers** (measured 2026-10-28 on a development laptop against a local backend with a copy of the 2026-10-01 production index; not the production box)
- **Before** (plan section 3.2, production, busy box): chips removed 4, requests 4 pairs (8 requests), results area blank during each wait.
- **After:** 4 chip removals, 0 requests; one "Update results" press, exactly 1 search + 1 pins request (read from the page's fetch log and Playwright's request log, desktop and phone, light and dark). Sampling the page every 25 ms (394 samples) from the Update press until the new results landed: rows never fewer than 50, the text "Searching…" never shown, the Search button never disabled, the chips strip present throughout. A removal sequence that ended on "All parcels" (949,014 matches) took 9.5 s on this laptop for the single search.
- **Tests:** frontend 861 passed in 70 files (`npm test`); lint 66 warnings, 0 errors; `npm run build` passes (existing large-chunk warning only). New: `useDiscoverySearch.test.tsx` (16), `draftModel.test.ts` (11); updated `DiscoveryPage`, `DiscoveryResults`, `DiscoveryMap`, `chips` tests. Playwright: `discovery-responsive` and `discovery-map-m2` extended for the dimmed state and the camera policy; `npm run test:mobile` 45 passed, 20 intentional project skips (all 40 route/device overflow cells clean, Discovery included).
- **Reproduce:** `cd frontend && npm test && npm run lint && npm run build`; for the browser run, a local backend on :8001 with a copy of the index, `npm run dev`, then `npx playwright test e2e/discovery-responsive.spec.ts e2e/discovery-map-m2.spec.ts --project="Galaxy S24"` and `npm run test:mobile`.
- **Not measured:** latency on an idle production-class box (the plan's own caveat); a real Pro session (the e2e fixture mocks `/api/auth/me`); real screen-reader behaviour of `inert` and the live "Updating" status; touch devices (Playwright emulation only); Spanish string fit at 360 px; whether users find or forget the Update button.

## Item 2: the page asks for the list and the map's points in one request (`includePins`) (2026-10-29)

**Decision: `useDiscoverySearch` sends one `POST /api/discovery/search` with `includePins: true` and reads the map's points from `response.pins`; if the response carries none, it falls back to the separate `/search/pins` request.** The backend contract is Phase 1 (PR #131, decision record `2026-10_discovery-speed.md` Decision 5): `pins` is the `/search/pins` body computed from the same evaluation as the list. The fallback means deploy order cannot break the map: an older backend ignores `includePins`, returns no `pins`, and the page behaves as before (two requests, map failure isolated from the list).

**Item 30 still holds, and the checks stay.** The list is canonical, and the points are accepted only when data version, total and cardinality agree with it; otherwise the list survives and the map is explicitly unavailable. They are redundant when one evaluation produced both, and they stay on purpose: they are what makes a future backend or proxy regression visible instead of a silently wrong map. Item 30's "revisit if both windows move into one atomic response" is exactly this change; the answer is that the contract is kept and the failure mode changes. **One difference to know about:** with the combined request a failed request fails the list and the map together (the page keeps the previous results and shows "Couldn't update. Retry", as Phase 0 already does); before, a failed pins request alone left the list valid. Only the fallback path keeps the old isolation.

**Load more** and **export** are unchanged: load more asks for the next window only (no `includePins`), and export still uses `/search/export`.

**Alternatives.** (1) Switch unconditionally and drop `runPins`: simpler, but couples the front end's deploy to the backend's and removes the rollback path. (2) Detect support from the registry or a version header: more machinery for a one-line check on the response itself. (3) Keep both requests: the backend now coalesces and caches them, so the cost is small, but the page would still hold two windows over what is one query.

**Numbers** (2026-10-29, local, backend from PR #131 with the 949,014-row production index copy, this branch's dev server)
- One chip removal, then "Update results" (a 3-filter query, 7,531 matches): 0 requests for the edit, then exactly 1 request, `POST /api/discovery/search` with `includePins: true`, and none to `/search/pins`; the map key counted 5,000 points (502 + 1,079 + 199 + 3,220) and the console had no errors. Read from the page's fetch calls in the in-app browser.
- Tests: frontend 869 passed in 70 files (was 861 in 70 on the Phase 0 branch); lint 66 warnings, 0 errors; `npm run build` passes. New: seven `includePins` tests in `useDiscoverySearch.test.tsx` (embedded points accepted; wrong data version, wrong total and wrong cardinality each withhold the map; fallback when no points; failed fallback isolates the map; no second request when points are present; load more never asks for points) and one in `searchClient.test.ts`; the Phase 0 "pair" tests now assert one request.
- **Not measured:** the Playwright specs (`discovery-responsive` now accepts 1 or 2 requests per press, depending on the backend) were edited but not run here; no production traffic; the latency gain is the backend's (Phase 1), this change is the contract and one request instead of two.
- **Reproduce:** `cd frontend && npm test && npm run lint && npm run build`; for the browser check, run the PR #131 backend on a local port with an index copy, `VITE_API_BASE=http://localhost:<port> npm run dev`, press Update results and read the requests.

**Revisit if** the backend adds a server-issued query id (then the cardinality checks could be replaced by it), or the combined request's failure coupling proves annoying (then a separate map retry could be added).

## Item 3: Phase 2, a Start panel instead of a silent auto-run, and the first-screen honesty fixes (2026-10-29)

**Decision: nothing runs on arrival. Until the first search the page shows a Start panel, and every way in from it is one explicit "search this".** This replaces the 2026-07-01 auto-run of the first live recipe (the plan's Q1, decided 2026-10-29). The auto-run existed so the page never opened dead; its cost was a search nobody asked for, with four filters applied and never explained. The panel offers a recipe, one neighborhood, every parcel, or this browser's last search. It renders no result of any kind, so there is nothing to mistake for one. It shows only while `!response && !loading && !unavailable`: it goes away the moment a search starts and does not come back, and a failed first search shows the old "Search unavailable" state, not the panel. *Alternatives:* keep the auto-run and label it (kept the unexplained search); open on an empty map and an empty list (a dead page, the original objection).

**Decision: a recipe card says what it filters by reading its own presets, not by a hand-written line.** The plan called for a registry `why` string per recipe. A line built from the preset predicates (`chipLabel` over `topic.presets`, for example "Filters: Vacant · Zoning group: Residential (R) · Near transit ≤ 0.5 mi · Lot size ≥ 3000 sqft") cannot drift from what the recipe does and needs no backend or registry-schema change. **What it does not do is give a reason.** The reason for the 3,000 sq ft lot minimum is still undocumented (plan Q5: the owner writes it); nothing here invents one. A reason line can be added later as copy without touching this structure. *Alternative rejected:* write plausible rationales for five recipes (unsupported claims, source-confidence).

**Decision: the first recipe now says what it filters.** `vacant_mf_transit` compiles to `zoning_group = residential`, which is every R district (`index_build._zoning_group`: first letter R), but was labeled "MF-zoned" and "RM/RT multifamily zoning". It now reads "Vacant land in residential zoning near transit" / "(RS, RT and RM)". The id is unchanged (telemetry), the registry version is bumped to `2026-10-29.1`, and `test_discovery_copy_honesty.py` fails any recipe on the residential group whose label or description says MF, RM/RT or multifamily zoning. A real RM/RT filter needs an index field and is out of scope (index work, decision Item 36).

**Decision: the text box's example must parse completely.** The old placeholder ("vacant multifamily near the L, built after 1990") silently dropped "L". The new one ("multifamily built before 1950 with a TIF") compiles to three filters with an empty residual, and a cross-tree test reads the placeholder from `en/pages.json` and runs the backend compiler on it. The "Understood / Ignored" feedback and not searching when nothing was understood are Item 4.

**Decision: "Index built <date> · all N community areas" comes only from `registry.coverage`.** `asOf` and `liveAreas` are the only things the registry carries; there is no parcel count, so none is shown (the plan's "882,322 parcels" would have been a hard-coded number). It renders nothing without an index or a build date, formats a calendar date in UTC so a viewer's time zone cannot move it, and shows once (in the Start panel before a search, in the rail after).

**Decision: Resume keeps inputs and the evaluated sentence, in this browser only, and re-runs the inputs.** `localStorage` key `ul_discovery_last`, versioned, 30 days, every access guarded (private windows and blocked storage must not break the page). What is displayed on Resume is the sentence the server's cqs produced when it was saved; the results are evaluated fresh when the user clicks, never replayed (INV-4). *Alternative rejected:* store the result rows (stale data shown as current).

**Decision: a neighborhood start is a search for that one region and nothing else** (`neighborhood: ["neighborhood:<id>"]`, no recipe, default sort), offered only for indexed areas when coverage is partial. The user then adds filters to it in the rail (the "+ Add filter" strip is Phase 3).

**Telemetry:** `discovery_start_choice` `{kind: recipe | neighborhood | all | resume, id}`, added to the backend allowlist. It is the first measurement of which door people use; there was none before.

**Spanish is deferred** (owner, 2026-10-29): the new `es` strings are a first draft in Mexican Spanish, usted, for the pre-merge pass.

**Revisit if** Resume is rarely used or the panel is skipped immediately (the events will say), the Start panel's recipe list should be the "needs data" recipes quieter or last (they are listed in registry order today), or an index change makes a real RM/RT recipe possible.

**Numbers** (2026-10-29, local, this branch's backend with the 949,014-row production index copy, in-app browser)
- Load: 1 discovery request (`/registry`), no search, no results area; the Start panel with 6 recipes (5 live: 5,005 / 1,122 / 46 / 312 / 457; one "Needs data") and 77 neighborhoods.
- A neighborhood pick sent one search with exactly `{neighborhood: {kind: "region", regions: ["neighborhood:22"]}}` and no recipe; this backend predates `includePins`, so the page fell back to the separate pins request, as designed.
- After a reload, Resume showed the saved sentence with zero search requests before the click, then ran it (50 rows).
- Phone width (360): no horizontal overflow; the Start panel begins about 320 px down, where the first result row was about 1,370 px down (plan section 0, measured on the old page).
- Tests: frontend 896 passed in 73 files (895 before the as-of dedupe test; 869 on the includePins branch); lint 66 warnings, 0 errors; `npm run build` passes. Backend: discovery tests 201 (199 plus the two copy-honesty tests; this branch does not contain the Phase 1 backend), full suite 2,429 passed.
- **Not measured:** how often each door is used; Playwright (`discovery-responsive`, `discovery-map-m2`, `npm run test:mobile`) was not run for this slice; Spanish fit at 360 px; the light theme; a real Pro session.
- **Reproduce:** `cd frontend && npm test && npm run lint && npm run build`; `python -m pytest backend/tests/test_discovery_*.py -q`; for the browser pass run a local backend with an index copy and `VITE_API_BASE=http://localhost:<port> npm run dev`, open `/discovery`, and read the requests.

## Item 4: the text box asks the compiler before it searches (compile-only `text-preview`) (2026-10-29)

**Decision: `POST /api/discovery/text-preview` runs only the compile half of a search (`parse` then `merge`, the calls `/search` makes through `_resolve`) and returns `{understood, residual, droppedInvalid}`; the page asks it before searching a phrase.** The text box is a rule-based compiler (INV-5, no model) covering a few dozen phrases; it drops what it does not recognize. A phrase it understands none of ("teardown in logan square" compiles to no filters) used to search every parcel, silently. Now, when the draft has text and no panel filters, the page asks first; if nothing was understood it runs **no search**, keeps the previous results untouched, and says "I couldn't turn “…” into filters, so no search was run. Not understood: …", with an example that works. The choice was the owner's (2026-10-29). *Alternative rejected:* run the search and refuse to commit it afterwards (it still scans and caches a whole-index query nobody wanted, and the previous state is only protected by discipline).

**The gate fails open.** If the preview cannot be answered (network error, non-200), the page searches as before: the check must never be what breaks search. A draft with panel filters beside the text, or with blank text, searches at once with no preview (the filters carry the search). A newer apply, a text edit, a recipe or other Start-panel choice supersedes a check still in flight, so a stale answer cannot start a search the user has moved on from.

**INV-4 stays intact.** The preview is advisory: it drives the gate and the "nothing understood" notice only. After a search, the wording "From “…” I understood: …; Not understood: …" is built from the evaluated `response.cqs` (filters with `source: "text"` and `meta.textResidual`), never from the preview. A phrase understood completely says nothing (the chips already do). A search that ran on other filters while the text did nothing says so.

**Backend shape.** A new module (`text_preview.py`) with its own router on the same `/api/discovery` prefix, so the production proxy already routes it and it adds no code to `api.py` (which the Phase 1 PR rewrites). Text is capped at 500 characters (the compiler is linear regex, but the endpoint is anonymous). It reads no index and never evaluates. Tests: the preview equals what `/search` derives from the same text (filters, residual and drops, for four phrases); compile-time drops are reported; a test patches every `evaluate` under `backend.discovery` to fail if the endpoint touches it.

**The compiler is English-only, and the Spanish strings now say so.** A Spanish example phrase would be an example that does nothing, and the placeholder I wrote in the first Phase 2 slice had that flaw. Both Spanish strings now offer the English phrase and say "en inglés"; a test requires every example the page offers, in either language, to compile with nothing dropped. Whether the compiler should learn Spanish is a product decision, not made here.

**Revisit if** the compiler grows (then the example and the phrase list should come from one place), the preview adds noticeable latency (it is one small request per text search; not measured here), or the text box becomes a live-as-you-type control (the endpoint is cheap enough to debounce, but that is a different interaction).

**Numbers** (2026-10-29, local, this branch's backend, in-app browser)
- "teardown in logan square": 1 request (`/text-preview`), 0 searches, notice shown, Start panel still up. "multifamily built before 1950 with a TIF": preview, search and pins (this backend predates `includePins`), 50 rows, no feedback line. "vacant multifamily near the L, built after 1990": searched, feedback "I understood: Year built ≥ 1990 year; Property use: Multifamily; Vacant. Not understood: l."
- Tests: frontend 910 passed in 74 files (896 before); lint 66 warnings, 0 errors; `npm run build` passes. Backend: 9 text-preview tests plus the extended copy-honesty test (11 together).
- **Not measured:** preview latency in production; the Playwright specs; Spanish fit.
- **Reproduce:** `python -m pytest backend/tests/test_discovery_text_preview.py backend/tests/test_discovery_copy_honesty.py -q`; `cd frontend && npm test && npm run lint && npm run build`; or `curl -X POST <backend>/api/discovery/text-preview -H 'Content-Type: application/json' -d '{"text":"teardown in logan square"}'`.

## Item 5: Phase 3a, an "Add filter" menu with tiers, edit in place, and Discard changes (2026-10-29)

Phase 3 of the plan replaces the permanent 32-control rail with a "Your search" header and an "+ Add filter" menu. It is split in two so the risky half can be reviewed alone: **3a (this item) is additive and keeps the rail**; 3b removes the rail and moves the text box and sort. Nothing in 3a takes anything away.

**Decision: each registry filter carries a presentation `tier` (`essential` or `more`), and liveness stays the index's `populatedFields`.** The menu lists live filters in two groups (Essentials: Neighborhood, Property use, Vacant, Lot size, Zoning group, Near transit, Sold within, the owner's Q3 answer; then More filters: the other 12 with data) and keeps the 13 filters with no data in a collapsed "Coming soon (13)" row (the owner's Q4 answer). A filter with no data is "coming soon" whatever its tier, so a data refresh moves it into the live groups with no code change (`menuGroups`, tested). Tier is registry data (version `2026-10-29.2`), pinned by a backend test, and a test fails if any evaluation-side module reads `.tier` (INV-1/INV-6). *Alternative rejected:* hard-code the list in the front end (two sources of truth).

**Decision: one popover, two views, reusing the existing control unchanged.** "+ Add filter" opens the menu (search box focused); picking a filter shows its existing `Control` (exported from the filter panel, not rewritten, so Phase 3b can rework it once) with "Reset this filter" and "Done". A flag adds as "Yes" at once, since there is nothing to pick but a side; every other kind opens an editor and adds nothing until the user gives it a value. Clicking a chip's label opens the same editor for that filter (the x still removes; a struck-through chip still restores). Everything edits the **draft**, so Phase 0's "Update results" model is untouched. A popover on desktop and a bottom sheet below `md`; Escape or a click outside closes it (clicks on its own anchors are theirs, so it does not close-and-reopen), and focus returns to the opener.

**Decision: "Discard changes" replaces the plan's "Undo".** It puts the draft back to exactly the query last evaluated (its user filters, the text that was sent, its sort) and requests nothing. The draft model already knows the applied query, so this is one pure function (`discardToApplied`) and it fixes the old gap where "Clear all" left the page describing a different query than the panel. A multi-step history stack would be more machinery than the use case needs. It shows only when there are pending changes and a search has been evaluated.

**Decision: the upside score is tagged "heuristic" where a user meets it** (menu row, editor header, and its chip's tooltip), with the plain sentence the registry already carries about what it is: a 0 to 100 score from unused zoning capacity and land-versus-building value, a rough v1 heuristic that helps rank candidates, not an appraisal. It is not given more prominence (plan section 8).

**Not in 3a (3b):** removing the rail and its recipe shelf, moving the text box and sort into the header, collapsing the title once a search is active, and giving the freed width to the map. The old accordion stays in the code until then.

**Revisit if** the essentials list does not match what users reach for (the existing `discovery_search` event carries no per-filter data; adding a `discovery_filter_edit` event is the plan's way to find out and is not in this item), or the seven essentials include one that the Start panel's recipes already cover.

**Numbers** (2026-10-29, local, this branch's backend with the 949,014-row production index copy, in-app browser)
- Menu on desktop: Essentials = 7 rows, More filters = 12 (upside tagged "heuristic"), "Coming soon (13)" collapsed; the search box takes focus. Editing Lot size to a 5,000 minimum made one pending chip, "Update results (1)" and "Discard changes", with **0 requests**; Discard cleared them with 0 requests; adding TIF from the menu and pressing Update sent one search (plus the separate pins request, since this backend predates `includePins`) and 50 rows came back; Done and Escape both closed it.
- Phone (390): a full-width bottom sheet with a backdrop, no horizontal overflow, 19 tappable rows.
- Tests: frontend 944 passed in 76 files, run three times (no flake; one pre-existing flake in the earlier text-gate test was found and fixed on that branch); lint 66 warnings, 0 errors; `npm run build` passes; backend 2,440 passed (registry tier tests included).
- **Not measured:** the Playwright specs and `npm run test:mobile` (the rail is unchanged in 3a); the light theme; Spanish fit at 360 px; which filters users actually pick.
- **Reproduce:** `cd frontend && npm test && npm run lint && npm run build`; `python -m pytest backend/tests/test_discovery_registry.py -q`; for the browser pass run a local backend on an index copy, `VITE_API_BASE=http://localhost:<port> npm run dev`, search, then use "+ Add filter".

## Item 6: Phase 3b, the filter rail is removed; the page is a results column with a search header, and the map (2026-10-29)

**Decision: the permanent left rail is gone.** Before, every first-time visitor met a 32-control rail beside the results; Phases 2 and 3a gave every job the rail did a better home, so 3b removes it. The page is two regions: a **results column** (460 px at xl, 580 at 2xl) and the **map**, which takes the freed width (about 560 px before, 980 px at a 1440 px viewport after). Before the first search the column is the Start panel; after it, the column is a **search header** over the list.

**The header, top to bottom:** the describe box and Search (plus the `TextFeedback` line under it); "New search" (and, below xl, the List|Map toggle); the chips strip with "+ Add filter", then "Update results (n)" and "Discard changes" when something is pending; the evaluated summary sentence with **Sort beside it** (it used to sit beside Search, far from the list it orders), then "Ask the analyst" and the index-as-of line. The page title is the Start panel's `h1` before a search and a screen-reader-only `h1` after (the plan's "title collapses once a search is active"); there is always exactly one.

**Decision: below xl the header stays above both tabs.** The old rail was the only thing visible on the phone Map tab, and the page duplicated the Update button into it to cope. Now the results column always holds the header; on the Map tab only the list under it is hidden. Update results exists once on every tab, and the old duplicate and its test are gone.

**Decision: "New search" is the way back to recipes.** With the rail's recipe shelf gone, nothing else leads back to the Start panel. `startOver` abandons anything in flight (a late response is ignored), clears the results, map and draft, and returns to the panel, where the search just run is offered again as Resume (the page re-reads the saved search; the first version of this read it only at mount, which a test caught). It requests nothing. This amends Item 3's "the panel does not come back": it comes back only on this explicit action.

## Item 7: Phase 4, the phone gets the screen: a collapsed header, a Show results sheet, 44 px targets, and honest map and error states (2026-10-29)

**Measured first (390x844 and 375x667, the 3b page, production index copy):** the search header was 381 px (45% of the screen) on an iPhone 15 and **415 px (62%) on an iPhone SE**, pinned above a list that scrolls inside what is left: 196 px on the SE, one result row. Every touch target was under 44 px (Search 36, Add filter 26, chips 26, New search 17, List/Map 29, sort 31 by 28, Ask the analyst 27) and the chip x was 10 by 10 px.

**Decision: below `md` the header collapses after a search.** It becomes "New search | List/Map", one full-width summary button (the first filter and "+N more", read from the DRAFT's chips, which are a control surface and not a claim about results) and the Update row. Describe box, chips, "+ Add filter", the evaluated sentence with Sort, "Ask the analyst" and the index line open on tap. It **opens by itself** when something needs attention (an unapplied edit, a "nothing understood" notice, no matches, a failed search, the Add filter menu), and a **new result collapses it again**: the open state is keyed to the response object the user opened it for, so no effect is needed. Tablets and desktop are unchanged. Flex `order` keeps the desktop order while the phone order puts the always-visible parts first. *Alternatives rejected:* a sticky mini-bar over a scrolling header (changes how the list scrolls and how infinite scroll roots), and only trimming the expanded header (the gain is too small).

**Decision: the Add filter sheet applies edits from a sticky footer on phones.** "Show results (n)" applies the pending edits and closes the sheet; with nothing pending it is "Done". Edits stay draft-only until then (Phase 0's model), so nothing is requested while the user taps through filters.

**Decision: 44 px touch targets on a coarse pointer only; mice are unchanged.** Two shared CSS utilities in `index.css` behind `@media (pointer: coarse)`: `.touch-target` / `.touch-field` give real buttons and inputs a 44 px minimum, and `.touch-hit` leaves small pills and the chip x looking as they do while extending an invisible 44 px hit area (`.touch-hit-x` is taller than wide, because the x sits beside the label's own target). The x is in the shared `Chip` primitive, so removable chips elsewhere get it too. The Playwright spec asserts the real sizes and hit-tests the x and the Add filter pill at 17 px above and below their centres; a probe at 20 px lands on the neighbouring control's own target, which is correct, so the spec uses 17. *Alternative rejected:* growing the chips to 44 px (heavy-looking).

**A real bug the device run found: Safari ignores padding and min-height on a native `<select>`.** The sort select measured 20 px on every iPhone profile while Chromium measured 31. It is now `appearance-none` with its own arrow, which every browser sizes the same.

**Decision: what the map leaves out is named inside the counted key.** The "N of M plotted / outside the map cap" box in the bottom-left is gone; the same lines are the foot of the key, which already counts from the same model. On phones the key sits behind a "Map key" button, so that button carries a second line, "5,000 of 5,005 shown", whenever matches are missing, which keeps Item 31's "name every omission" true while the key is closed. Zoom to results and the stale note moved to the right edge on phones to make room.

**Decision: zero and error states.** The zero-result reasons move from `text-micro` to the page scale (`text-caption`), the relax chips grow and get the hit area, and the zero state offers **Discard changes** when there are unapplied edits. A failed first search now has a Retry button. *Not built, and worth knowing:* a true "back to the previous results" (the plan's "Undo last change") is now cheap, because the result cache makes the previous query instant, but the approved design offered only Discard changes, so it is a follow-up. *Skipped on purpose:* the "slow search" message; Phase 1 made broad searches about half a second locally, and production is unmeasured (a read-only re-measure needs the owner's approval).

**Spanish and the light theme, finally checked.** Spanish at all five device widths (360 to 430): nothing in the collapsed or expanded header or the sheet extends past the viewport or clips its text. A string-length budget test (`phoneStrings.budget.test.ts`, the sibling of the nav budget) now holds the phone control labels to a per-locale limit and fails on a multi-word label left in English. It also found one: Spanish `mapKey` was still "Map key" (now "Leyenda del mapa", and removed from `_untranslated.json`). Light theme: screenshots of the collapsed header, the expanded header and the sheet were looked at and read clearly. The Spanish strings are still a first draft for the pre-merge Mexican-Spanish pass.

## Item 8: the Spanish pass on Discovery (Mexican Spanish, formal *usted*), before the redesign reaches `main` (2026-10-29)

**Decision:** every Discovery string in `es/pages.json` is Mexican Spanish in the formal *usted* register, and the 16 map and search messages that still showed English are translated. Jack's rule is "Mexican Spanish" (2026-10-29), and he then chose the formal *usted* register for the whole app ("Usted everywhere"), because the audience is construction and real-estate professionals.

- **Register fixed in Discovery only.** Eight strings used *tú* (`subtitle`, `searchAria`, `teaserCount`, `teaserUnlock`, `mapTruncated`, `setFilters`, `scrollMore`, `zeroTooTight`) and two new ones did (`chipPendingTitle`, `restoreFilterTitle`). The same commit series then converted the 43 remaining *tú* strings in `common`, `chat`, `landing`, `sidebar` and `pages` (settings, not-found, Property Profile) to *usted*, plus *subidos* to *cargados* (uploaded files) and *gestiona* to *administre*. The $25 report catalog (`backend/report_i18n.py`) already had no *tú* forms. *Alternative:* keep *tú* outside Discovery; rejected by Jack.
- **Vocabulary.** *Agregar* for *añadir* (3 strings), *terreno* for *suelo*, *subutilizada* for *infrautilizada*, *zona inundable* for *llanura de inundación*, *solicitudes 311* for *denuncios 311*, *índice de delincuencia* for *criminalidad*, *intente* for *pruebe a*. The start panel's neighborhood and parcel words follow the app glossary (*vecindario* 14 uses, *parcela* 75) rather than the *colonia* and *predio* the build session introduced.
- **Left as is, flagged:** *subvenciones* (grants, 2 uses app-wide; *apoyos* or *subsidios* may read more naturally in Mexico), *llanura de inundación* in other namespaces, *criminalidad* in 2 non-Discovery strings.
- **The 16 untranslated keys** (`mapAria`, `mapIdle`, `mapLoading`, `mapUnavailable`, `mapEmpty`, `map*_one/_other`, `mapSummary`, `legendLandUseNoData`, `searchUnavailable`) are translated and removed from `es/_untranslated.json`, which the guard test requires.
