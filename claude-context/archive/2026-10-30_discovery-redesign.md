# Property Discovery redesign (Phases 0–4), its Spanish pass, and the index prune

**Completed:** 2026-10-30 · **Status:** Shipped to production. Phase 1 backend speed in PR #131 (`8e3925d`, 2026-10-29); Phase 0 draft/apply plus the one-request list-and-map (`includePins`) in PR #132; Phases 2–4 (Start panel, text gate, Add filter menu, rail removed for a results column + map, phone layout) were stacked PRs #133–#136 that reached `main` through PR #139 (`b237066`, 2026-10-29) together with the Mexican-Spanish, formal-*usted* pass; the chat answers in Mexican Spanish since PR #140 (`1ccf307`, 2026-10-30). The production index was pruned of 66,692 suburban rows on 2026-10-30 (949,020 → 882,328; builder fix PR #128, dashed-PIN prune fix PR #137, `backend/discovery/index_prune.py`), and the monthly `discovery-index-rebuild` unit got a 12 h start timeout and a clean stop/reload (PR #142). A flaky draft-edit test got a wait for its chips (PR #145; not reproduced). **What changed for a user:** nothing runs on arrival (a Start panel offers recipes, a neighborhood, all parcels or Resume); edits are drafts until "Update results (n)"; the previous results stay, dimmed, while a refresh runs; the text box says what it understood before searching; filters come from an "Add filter" menu instead of a 32-filter rail; the phone gets a collapsed header and a Show-results sheet. **Lessons:** (1) make a search an explicit act: auto-running on every edit made the page feel slow and lie about what the list showed; (2) keep the old results on screen while the new ones load, so a refresh never blanks the page; (3) a prune that runs against a different key format than the one stored deletes nothing and logs nothing — test with the production row shape (`pin` dashed), not a convenient one; (4) stacked PRs merged through the top of the stack leave the lower PRs "closed", so record the carrying PR.
