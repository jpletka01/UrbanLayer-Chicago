# Code refresh: the monthly routine

**Status (2026-10-22): WS1 M7.** What keeps the municipal code text, and what Council has passed since it, honest. Read this when the monthly reminder email arrives, when the Data health panel shows the code text or the amendment review as warn/alarm, or before any new export goes in.

**Why it is manual.** American Legal Publishing (the code library) has no feed, and its contact route leads to a paid subscription, so a person downloads the full-code HTML export. It runs about two to four months behind Council (the 2026-05-28 download was "current through March 18"; the 2026-10-21 one, June 17). The City Clerk's public API fills the gap: it lists everything Council passed since, and the product says so on every surface (Profile note, section viewers, chat, the $25 report). So a refresh is two jobs: **review what Council passed** (monthly, 1 to 2 hours) and **ingest a newer export when one exists** (half a day).

## The signals, and what each asks of you

All on the Data health row of `/admin` (and `GET /api/admin/data-health`); the Code currency card on the same page has the amendment list.

| Source id | Goes red when | What to do |
|---|---|---|
| `internal.amendment_review` | a **Title 17** amendment has waited more than 14 days since Council passed it without a review (warn), more than 45 (**alarm, Sentry email**); any other passed amendment waits more than 45 (warn only) | Do the monthly review (below). It is its own source because `code.municipal_text` is acked; an alarm there would show "acked" and never email |
| `internal.pending_impact_review` | a **pending** Title 17 text proposal (still in committee) has no current review in `backend/pending_impacts.json` more than 14 days after Council introduced it (warn), more than 45 (**alarm**); or its review is of an older record than the live substitute ("outdated"); an invalid review entry alarms | Do the pending-amendment review (below) |

## The monthly review (after each City Council meeting)

Council meets roughly monthly (2026: May 20, June 17, July 15, Sept 23, Oct 14), so expect two to four new Title 17 amendments each time. No export is needed for any of this.

1. **Look.** `/admin` → Data health and Code currency: new passed amendments since the last review, the unreviewed count, rezonings and landmark designations passed but not on the City map, titles the parser could not read. From a terminal (reads the Clerk, writes nothing): `python -m backend.legislation.sync --print`.
2. **Review each new amendment.** For a codified one, read the section diff in the refresh's `report.md`. For one not yet in the text, read the passed ordinance: for a substitute, the `SO…` "Legislation" or "Final Ordinance" attachment, **never the Economic Disclosure Statement**; the matter link is on the Code currency card. Then add or complete its entry in `backend/code_amendments.json` (the file's `_readme` and `schema` say the fields). The ones that matter:
   - `summary` (what it does, from the text in hand) and `sections` (the sections it changes); `summary_basis` / `sections_basis` say where each came from: `ordinance` (the passed PDF was read) or `code_text` (read from the codified text of the export that carries it). A summary stays null until someone has read one of them;
   - `review_status: "reviewed"`, `reviewed_on`, `reviewed_by`;
   - `product_effect`: `none` (chat simply retrieves the new text), `applied` (the product states it ahead of codification, see step 3), or `pending`;
   - `codified`: whether it is in the text **we serve**; `codified_partly` for an omnibus only part of which is in (its `sections` then list only what is not);
   - `map_effects`: street segments for a pedestrian-street or TOD-street change; `relevance` (`title17` / `cited_other`) is set by the classifier and overridden only with `relevance_basis: "review"`.
3. **Decide the product effect, by where it lands.** Rule logic (`adu_status`, `tod_benefits`, minimum lot area per unit, the bulk table); overlay facts (`overlay_facts.py`); use summaries in `zoning_definitions.py`; prompt rules; report strings. **Applying law ahead of codification** is `backend/legislation/applied.py` plus a transcription of the ordinance in `backend/tests/fixtures/ordinances/`; every rule is pinned to that transcription until the code text carries it, then to the text (`test_applied_law.py`). The wording is "passed on <date>", never "in effect since": some ordinances take effect after publication.
4. **Map titles the parser could not read** (listed on the card, and by `sync --print`) go in `backend/rezoning_overrides.json`, each checked against the ordinance PDF. A partial parse never flags a parcel; an override makes one flaggable.
5. **Check American Legal's "current through" date** at `codelibrary.amlegal.com` (Chicago). If it has moved past at least one Council meeting since our vintage, download the export and run the refresh below.
6. **If any zoning fact changed,** run the free Profile kit: `PYTHONPATH=. python -m eval.parcel_kit --full https://urbanlayerchicago.com --surfaces profile --out-dir eval/results/$(date +%F)`. **Never the chat kit for this**: it spends the production Anthropic key (about $1.20). The monthly chat accuracy run is a separate production check that Jack approves.

### The pending-amendment review (WS2 PR3; same meeting, a different file)

The Profile's "Pending zoning-code changes" block names a proposal only through `backend/pending_impacts.json`. Each Council meeting adds a handful of Title 17 text proposals to the Clerk's committee docket, and until each is reviewed every Profile says "N pending proposals haven't been reviewed" (and `internal.pending_impact_review` warns after 14 days).

1. **Look.** `python -m backend.legislation.pending --print` (reads the Clerk, writes nothing) or `/admin` → Data health. A record in the store with no entry under its lifecycle id is unreviewed; an entry whose `reviewed_record` differs from the live record (a new substitute) is outdated.
2. **Read the Legislation PDF** (the matter link; **never the Economic Disclosure Statement**; scanned PDFs are read in the session). Add an entry keyed by lifecycle id: `reviewed_record`, `basis: ordinance` plus `summary` (what it would change, from the text) and `impacts[]`; or `impacts: []` with a `no_impact_reason`. Say which pages were read (`pages_read`). A title-only entry (`basis: title`) may only say "no Profile fact"; never use it to claim an effect.
3. **Map each impact** to Title 17 `sections`, the Profile `fact_ids` it could change, and the deterministic `applies_when` (zone regexes, overlays, `facts_all`, `address_ranges`). The Profile must actually show the fact. Use `reach: untested` with a `reach_note` when the effect depends on something the Profile can't test (a map boundary, lot width). Word `could_change` with "would"/"could", never as adopted.
4. **Test, then commit** the review file with `backend/tests/fixtures/clerk/pending_title17_text_<date>.json` (re-record the population: the tests require every recorded pending matter to have a current review) in one PR. When a proposal passes it leaves the pending store and enters the passed-amendment review above.

Commit the review file with its tests in one PR. A pure review (no export) changes only data and tests, so it deploys the new `code_amendments.json` and nothing else.

## Refreshing with a new export (half a day)

Everything runs from the repo root with `.venv` active and local Qdrant up (`docker compose up -d qdrant`). **The export is ~100 MB and not committable:** `.gitignore` has `chicago-il-*.html`, so never `git add` it, and keep each export under its own name (the 2026-06-17 one is `chicago-il-1-june.html`).

1. **Download** the full-code HTML export from the code library and note its header, "Current through Council Journal of <date>". If that date is still our vintage (`backend/code_vintage.json:current_through`), stop: there is nothing newer.
2. **Dry run.** `python -m ingestion.update --dry-run --source <export>`. It parses into `ingestion/data/sections.new/` and writes `ingestion/data/diff/<vintage>/{diff.json,report.md}` (per-title counts, added/modified/deleted sections, text diffs for Title 17 and the cited sections, the `Coun. J.` dates found) and checks the **abort gates**: vintage not newer, any title losing more than 2% of its sections, Title 17 shrinking, new empty Title 17 bodies, a changed parse table. It touches nothing else. A tripped gate is a parser regression until proven otherwise; American Legal has changed markup before and Title 14 once vanished wholesale. The 2026-06-17 refresh tripped Title 13 on a **real** repeal, confirmed by the export's editor's notes ("Reserved", citing Coun. J. 6-17-26): read the notes before `--force`.
3. **Codification check.** `python -m backend.legislation.codification_check --diff ingestion/data/diff/<vintage>/diff.json --sections ingestion/data/sections.new` (`ingestion/data/sections` once step 4 has promoted them). For each passed amendment dated on or before the new vintage it looks for a section whose history cites that Council Journal date: *matched* = codified; *missing* = American Legal skipped it, so it stays in the "since" list; *partly* = an omnibus where only some sections changed. The reverse check lists modified sections with a journal date nobody classified. **Read the section diff before trusting a match**: titles overstate (SO2026-0024923 and O2026-0024064 were narrower than their titles). Add `--write` to record `codified` in `backend/code_amendments.json` (it never flips a `codified_partly` entry).
4. **Apply locally.** `python -m ingestion.update --source <export>` (`--force` only once a gate is explained). It embeds into a new collection `municipal_code_<vintage>`, checks the point count equals the chunk count, and only then moves the old corpus to `ingestion/data/snapshots/<old vintage>/`, promotes the new files, flips the local `municipal_code` alias, and writes `backend/code_vintage.json` and `backend/code_changes.json`. The served collection is never edited. It takes about 6 minutes.
5. **Run the corpus-pinned tests,** which read `ingestion/data/sections/`: `python -m pytest backend/tests/test_zoning_ordinance_parity.py backend/tests/test_code_sections.py backend/tests/test_overlay_facts.py backend/tests/test_coverage_notes.py backend/tests/test_tod_benefits.py backend/tests/test_zone_standards.py backend/tests/test_provenance.py backend/tests/test_zoning_freshness.py -q -m "not integration"`. **Resolution rule: every failing pin is resolved with the new text open, either the law changed (update the rule, citation and annotation) or only the format or numbering did (fix the reader or citation). Never change a number to make a test pass without the ordinance text in hand.** The 14 pinned sections are committed in place under `ingestion/data/sections/`, so CI runs these tests too; the diff shows what changed.
6. **Review the newly codified amendments** as in the monthly review. Check three things the code cannot: Title 14M/14G/14N text in chat (the omnibus replaced it effective 2026-10-01 and the export still carried the old text), the CHRS note's `14A-4-407.6`, and the use summaries (`_C1_USES`, `_C2_USES`) against the use table.
7. **Zoning cache, with no model.** `python -m backend.zoning_cache_build --check` says stale if any Title 17 section changed, because the fingerprint covers all of Title 17. **Do not run the build without Jack's OK: it calls the production Anthropic key** (about $0.70). The builder reads five sections (17-2-0300, 17-3-0400, 17-4-0400, 17-5-0400, 17-10-0200). If their `content_hash` is identical in the old and new manifests, re-stamp `_meta.corpus_fingerprint` and `_meta.code_vintage` and record why in `_meta.fingerprint_rebased` (see the 2026-10-21 entry for the shape). If one changed, re-read it in-session and update the affected cache entries by hand, labeled as such, or ask for the build.
8. **Hand table.** Set `VERIFIED_AGAINST` in `backend/retrieval/zoning_definitions.py` to the new vintage only after the parity test passes against the new text.
9. **Push the index to prod** (needs Jack's OK; **alias first, then the code deploy**, so the product understates how current the text is for a few minutes rather than overstating it). Qdrant publishes no host port in prod: tunnel to the container. `jack` is not in the docker group, so find its address without sudo, from the server's neighbour table: `ssh urbanlayer-prod 'ip -4 neigh show'` lists the docker bridge hosts, and `curl <addr>:6333/` on the server identifies Qdrant (never commit the address). Then:
   ```bash
   ssh -f -N -L 6335:<qdrant address>:6333 urbanlayer-prod
   python -m ingestion.push_index --target http://localhost:6335 --status
   python -m ingestion.push_index --target http://localhost:6335 --upload     # ids and vectors copied, nothing re-embedded
   python -m ingestion.push_index --target http://localhost:6335 --verify     # per-section chunk-hash multisets; must be 0 differences
   python -m ingestion.push_index --target http://localhost:6335 --switch     # re-verifies, then flips the alias atomically
   ```
   Check from outside: `curl -s https://urbanlayerchicago.com/api/code/section/17-2-0304-A` (the response's `current_through` stays the old date until step 10 deploys, which is the intended order).
10. **Open the PR** with `code_vintage.json`, `code_changes.json`, `code_amendments.json`, rule and fixture changes, `zoning_cache.json`, kit and key updates, and docs; **ask before pushing and again before merging**. After the deploy, verify through the live API, not the server's git HEAD: `/api/code/section/17-2-0304-A` returns the new `current_through`, and `/api/scorecard?address=1601+N+Milwaukee+Ave` shows `code_currency` with the new vintage and a shorter "since" list.
11. **Kit and key.** Run the Profile kit (monthly step 6) before and after the deploy and compare cell by cell. A changed score is either law (update `eval/kit/parcels.json` with a `corrections` entry: date, parcel, field, was, now, the ordinance number; bump `version`; move `code_current_through`) or a regression (fix it before deploying). If the weekly gate's baseline should move after a reviewed improvement: `python -m eval.kit_gate <parcel_kit.json> --update-accepted`. Re-read the parcels that cite what changed (P5 for the Milwaukee Avenue overlay, P9 and P12 for transit-served-location rules, P10 and P12 for waste and gas-station changes). `make benchmark` and `make review-packet` regenerate the public pages from committed results.
12. **Clean up one refresh later,** not now: drop the oldest collection on prod with `python -m ingestion.push_index --target http://localhost:6335 --drop <name>` (it refuses the served one). As of 2026-10-22 prod still holds the unserved `chicago_municipal_code` and the rollback `municipal_code_2026-03-18`; keep the previous vintage as the rollback.
13. **Re-decide the acks** if the ack date on `code.municipal_text` is near, and write the refresh up in `claude-context/decisions/` (one file per build arc; its README gives the format, ending in a Numbers block).

## When something is red

- **The sync is `failed` or the snapshot is older than 72 hours.** The product keeps the last good rows and says "as of <date>"; after 14 days it withholds the count ("couldn't check recently") rather than saying none. Run it by hand on the server (`sudo systemctl start legislation-sync.service`, then `sudo journalctl -u legislation-sync.service -n 30 --no-pager`; `status=ok` and the counts are on the first line).
- **The snapshot is `suspect`.** The Clerk's response shape changed (BETA API, no versioning). The sync keeps the last good rows and the daily checker errors on `chi.clerk.legislation` with the problems listed. Run the contract test (`python -m pytest backend/tests/test_clerk_contract.py -m integration`, which calls the Clerk, free) and fix `backend/retrieval/clerk.py` against the recorded fixtures in `backend/tests/fixtures/clerk/`.
- **A passed rezoning or designation never leaves the "not on the map" list.** The City map takes more than 90 days for some, and every parcel flagged is a promise that the map is behind. If one is still off the map after 180 days, the lookback window drops it; measure with `PYTHONPATH=. python -m eval.designation_backtest` and `eval.rezoning_backtest` (public data, no model).
- **Rollback and skew.** The served alias and `code_vintage.json:collection` must agree. `push_index --status` shows both. Rollback is one flip: `--switch --to municipal_code_<previous vintage>` (then deploy the previous `code_vintage.json`, or the product will overstate the text).

## Rules that apply to all of it

- **No production Anthropic key for build work.** That rules out `zoning_cache_build`, the chat kit, `--judge` evals and any script that calls the model. Read what needs reading in the Claude Code session and commit it as labeled data (WS0: say it was read by a person or by AI, from what).
- **Government sources first, and say what you don't know.** A summary is written from the text in hand (`summary_basis`), never from a title alone. Interpretive calls are flagged in the PR for the outside reviewer.
- **Free tiers only; be polite to public APIs.** The Clerk, Census Reporter and Address Points are free: low concurrency and a pause between requests. Census Reporter answers 429 to a burst.
- **Pushing to `main` deploys.** Ask before pushing the branch and before merging; verify the deploy against the live API.
